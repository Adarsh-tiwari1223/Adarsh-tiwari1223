When I started building our Playwright test suite, I did what almost every tutorial shows:

I put locators, button clicks, API calls, and assertions directly inside the Page Object classes.

It worked fine for 10 or 15 tests.

Then our application started growing.

A developer changed one submit button ID, and 12 different test files failed at once. 
When we added multi-step flows like employee onboarding and payroll approvals, my employee_page.py blew up to over 400 lines of mixed code.
Worst of all, because assertions were baked into page methods, I couldn't reuse any of them for negative test cases.

That's when I stopped using standard POM and separated our suite into three simple layers:

1. Pages Layer
Only raw locators and simple actions (clicks, typing, dropdowns).
Strict rule: No business logic, no assertions. If a frontend selector changes tomorrow, I update it in exactly one place.

2. Workflows Layer
This is the piece most tutorials skip.
It handles user journeys that touch multiple pages—like logging in, onboarding an employee, and assigning assets. The test doesn't care which URL opens or which button gets clicked. The workflow handles the coordination.

3. Tests Layer
Pure test scenarios and assertions.
The test script stays short, clean, and reads like a plain checklist: call the workflow, pass test data, and assert the expected outcome.

If you are an MCA or engineering student trying to break into QA/SDET, here is something I wish someone told me earlier:

Don't just automate a simple login form and put it on your resume. Everyone does that. Show recruiters that you know how to build a framework that won't fall apart when 50 new features get added.
